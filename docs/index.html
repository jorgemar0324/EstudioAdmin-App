Sección 1

La Bala Trazadora y el Enrutamiento de las Skills

Cómo /grill-me alteró las asunciones iniciales

El Client Brief original describía una app sencilla: crear proyectos, agregar tareas, cronometrar sesiones. Antes de escribir una línea de código, la skill /grill-me interrogó cada asunción con preguntas que el brief no respondía.

Ejemplo concreto: El brief decía "ver un dashboard simple con horas de la semana". /grill-me preguntó: ¿la semana es lunes-domingo o rolling 7 días? ¿Qué mínimo de minutos cuenta como sesión válida para la racha? ¿La racha se rompe si el usuario no estudia hoy pero sí ayer?

Estas preguntas forzaron decisiones que de otro modo Ralph hubiera inventado: la semana es lunes a domingo (no rolling), el mínimo para la racha es 10 minutos de sesión, y la racha se cuenta desde ayer hacia atrás — lo que evitó un bug de estado donde el usuario pierde su racha si aún no ha estudiado hoy.

El árbol de diseño recorrido por /grill-me produjo 20 decisiones documentadas antes de que Ralph tocara el repositorio. El PRD resultante no fue una lista de features — fue un contrato de comportamiento exacto.

La Bala Trazadora: el issue más arriesgado primero

La analogía de la Bala Trazadora (Tracer Bullet) propone atacar primero el camino de integración más incierto del sistema para obtener feedback arquitectónico temprano.

En este proyecto, el issue más arriesgado no era crear proyectos ni listar tareas — era el issue 008: timer de sesiones de estudio. Este issue requería:

🔗 Integración de 4 capas

Frontend timer local → API REST → Prisma → PostgreSQL en Supabase, todo en tiempo real sin polling.

⚡ Estado global de React

El timer activo debía ser visible en la Navbar desde cualquier página — requirió Context API global.

🔄 Caso edge crítico

Sesiones huérfanas: ¿qué pasa si el usuario cierra el navegador con una sesión activa?

⏱️ Sincronización de tiempo

El timer frontend se calcula desde startedAt del backend — no desde el estado local — para sobrevivir recargas.

Al forzar a Ralph a implementar el issue 001 (monorepo + listar proyectos) como primera bala trazadora, obtuvimos feedback inmediato sobre la configuración de Prisma con Supabase, el proxy de Vite hacia Express, y los tipos compartidos en packages/shared — todo antes de construir features reales. Los issues 002-004 confirmaron que la arquitectura aguantaba. El issue 008 entonces fue ejecutado sobre cimientos verificados.

Issue 001 — Bala trazadora inicial

Monorepo + listar proyectos. Verificó: Prisma ↔ Supabase, Vite proxy, tipos compartidos.

Issues 002-004 — Confirmación arquitectónica

CRUD completo de proyectos y página de tareas. Confirmó que el patrón de rutas Express escalaba.

Checkpoint arquitectónico (entre 004 y 005)

/improve-codebase-architecture detectó 5 fricciones. Se refactorizó a Service Layer antes de continuar.

Issues 005-011 — Sobre cimientos limpios

Tareas, sesiones, dashboard. Cada issue ejecutado en <15 min gracias al Service Layer.

Issue 012 — RFC completado

Formalización del Service Layer como patrón oficial del proyecto.

Sección 2

Anatomía de la Complejidad

Módulos Profundos — Donde el agente acertó

Un Módulo Profundo (Ousterhout, cap. 4) oculta una complejidad algorítmica significativa detrás de una interfaz extremadamente simple. Los mejores ejemplos del proyecto:

📦 DashboardService.get() — Complejidad oculta detrás de una firma trivial

Esta función única recibe solo una fecha y devuelve tres métricas. Internamente ejecuta dos queries en paralelo, calcula la semana UTC, filtra sesiones válidas y cuenta rachas con lógica de fechas no trivial.

// Interfaz: una línea, un parámetro
async get(now: Date = new Date()): Promise<ServiceResult<DashboardData>>

// Internamente oculta:
// - getWeekBounds(): cálculo de lunes-domingo en UTC
// - calcStreak(): iterar días hacia atrás con Set de fechas
// - calcWeeklyHours(): filtrar por ventana semanal
// - Promise.all([sessions, projects]): queries paralelas

El caller (DashboardPage.tsx) no sabe que existen estas funciones. Solo llama useDashboard() y recibe los datos.

🚀 sendResult() — El helper más pequeño del proyecto

6 líneas que eliminaron todo el try/catch duplicado de las rutas. Cada handler del router quedó en exactamente 1 línea.

// Antes del refactor (cada ruta):
router.get('/', async (_req, res) => {
  try {
    const projects = await projectService.list()
    res.json(projects)
  } catch {
    res.status(500).json({ error: 'Error interno' })
  }
})

// Después con sendResult():
router.get('/', async (_req, res) =>
  sendResult(res, await projectService.list())
)

⚡ ActiveSessionContext — Estado global de timer sin prop drilling

El contexto expone una interfaz de 6 acciones simples (start, stop, discard, elapsedSeconds…) y oculta internamente: detección de sesión huérfana, timer local con setInterval, sincronización con TanStack Query y manejo de refs para evitar re-renders.

Módulos Superficiales — Donde la IA falló inicialmente

Un Módulo Superficial (Ousterhout, cap. 4) tiene una interfaz casi tan compleja como su implementación — no oculta nada significativo. El agente produjo este antipatrón en los primeros 4 issues:

⚠️ routes/projects.ts original — 172 líneas mezclando 4 responsabilidades

Ralph colocó validación, lógica de ordenamiento, acceso a Prisma y manejo de respuestas HTTP en un único archivo. Para entender cómo se ordenaban las tareas, había que leer todo el archivo.

// Antipatrón: constantes de negocio en la capa HTTP
const PRIORITY_ORDER: Record<string, number> = { ALTA: 0, MEDIA: 1, BAJA: 2 }
const VALID_TYPES = ['MATERIA', 'CURSO_ONLINE', 'SIDE_PROJECT']

router.post('/', async (req, res) => {
  // Validación inline...
  if (!name || name.trim() === '') return res.status(400).json(...)
  if (!VALID_TYPES.includes(type)) return res.status(400).json(...)
  // Acceso directo a Prisma...
  const project = await prisma.project.create({ data: {...} })
  // Respuesta HTTP...
  res.status(201).json(project)
})

Directriz aplicada: En el checkpoint arquitectónico (después del issue 004), se instruyó explícitamente a Claude: "Extrae toda la lógica de negocio a una clase de servicio por dominio. El router solo debe saber a quién llamar y cómo responder."

Fuga de Información — Detalles de DB filtrándose hacia la UI

Una Fuga de Información (Information Leakage, Ousterhout, cap. 5) ocurre cuando los detalles de implementación de un módulo se exponen hacia capas superiores. El proyecto tuvo dos casos concretos:

🔴 Caso 1 — Strings de Prisma expuestos como tipos en la UI

En los primeros issues, TaskCard.tsx comparaba directamente con 'COMPLETADA', 'EN_PROGRESO' — strings del enum de Prisma. Si el schema cambiaba, había que buscar y reemplazar en toda la UI.

Corrección: Los tipos TaskStatus, Priority, ProjectType se centralizaron en packages/shared/src/index.ts. La UI importa del shared package, nunca del schema de Prisma directamente.

🔴 Caso 2 — _count de Prisma expuesto en la respuesta de API

El endpoint GET /api/projects/:id retornaba el objeto _count: { tasks, sessions } directamente desde Prisma. El frontend tenía que saber que la propiedad se llamaba _count — un detalle de implementación del ORM.

Corrección parcial: Para el listado general, ProjectService.list() mapea a completedTasks y totalTasks — nombres semánticos del dominio. El endpoint de detalle aún expone _count y queda documentado como deuda técnica en el RFC 012.

Sección 3

El Veredicto Retrospectivo de los Sub-agentes

Las tres propuestas en conflicto

El checkpoint arquitectónico de Tarea 2 simuló tres sub-agentes con restricciones radicalmente distintas para resolver el mismo problema: cómo organizar el backend y el cliente API antes de implementar los issues 005-011.

Sub-agente 1 — Mínima
  • execute(cmd) dispatch
  • query() + mutate()
  • Superficie mínima
  • Autocompletado pobre
Sub-agente 2 — Máxima Flexibilidad
  • Repository pattern completo
  • Clases ApiClient por recurso
  • Máxima testabilidad
  • 14 archivos antes de lógica
✓ Híbrido elegido
  • Service por dominio (sin Repository)
  • ServiceResult + sendResult
  • Hooks de React Query
  • ApiError tipado

¿La interfaz elegida fue elástica frente al cambio?

La prueba real de una arquitectura no es cómo se ve en el papel — es cómo responde cuando llegan los últimos issues más complejos.

✅ Sin Change Amplification en los issues 008-011

El issue 008 (timer de sesiones) requería un nuevo endpoint PATCH /api/sessions/:id, un nuevo servicio SessionService, y un hook useSessions. Gracias al patrón del Service Layer, Ralph agregó exactamente eso sin tocar ningún archivo existente. El router de proyectos no cambió. La capa de hooks no se rompió.

El issue 011 (dashboard) fue el más complejo del sprint — lógica de fechas UTC, cálculo de racha, queries paralelas. DashboardService.get() encapsuló toda esa complejidad. El componente DashboardPage.tsx quedó en 80 líneas llamando a un único hook useDashboard().

Dónde sí hubo Change Amplification

El único punto donde agregar una feature requirió modificar múltiples archivos fue la constante PRIORITY_LABELS. Esta tabla de display (ALTA → 'Alta', etc.) quedó definida en ProjectsPage.tsx y fue re-definida en TaskCard.tsx. Cualquier cambio en los labels requeriría editar dos archivos — exactamente la Oportunidad 2 del checkpoint arquitectónico que quedó pendiente para el RFC 012.

Juicio final bajo el criterio de "buen gusto arquitectónico"

La decisión de no implementar la capa Repository del Sub-agente 2 fue correcta. Para un proyecto personal de un desarrollador, esa capa hubiera sido complejidad especulativa — lo que Ousterhout llama diseñar para un futuro que quizás no llegue.

La decisión de no usar el patrón Command/Dispatch del Sub-agente 1 también fue correcta. taskService.create(id, data) es descubrible en el IDE. execute({ action: 'create', projectId: id }) no lo es.

La solución híbrida demostró ser elástica: los 7 issues posteriores al refactor se ejecutaron sin fricción arquitectónica documentable. El HANDOFF.md no registra ningún bloqueante arquitectónico después del issue 005.
